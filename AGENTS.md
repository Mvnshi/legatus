# Notes for AI agents working on Legatus

Legatus runs coding agents (Codex, Claude Code) in parallel on one person's machine, spread across that
person's own logins, and keeps going when one of them hits a usage limit. You may be one of those agents, working
on Legatus itself in a git worktree that Legatus made for you. These notes are short on purpose; the design is in
[docs/DESIGN.md](docs/DESIGN.md) and what is and is not verified is in [README.md](README.md).

## Before you say you are done

Run these from the repository root. All three must be clean:

```sh
gofmt -l .          # prints nothing
go vet ./...
go test ./...       # takes a few minutes: the engine, queue and server tests start real git processes
```

`node --check internal/server/ui/app.js` is part of the server tests, so a JavaScript typo fails `go test`.

## Rules that are easy to break

- **Tests come with behaviour.** Every change that alters what Legatus does has a test that fails without it. Tests
  never need the network, a signed-in agent or GitHub; the real-world checks are gated behind an environment
  variable (`LEGATUS_LIVE_GH=1`). Use the existing stand-ins (`internal/agent/fake`, the scripted `gh` in
  `internal/github/github_test.go`, the helper-process pattern in the codex and claude tests).
- **Say what is true.** README and DESIGN state what was verified and what was not. If you add a claim, you also
  add the evidence, or you label it unverified. Do not make a feature sound finished when it is not.
- **Nothing is published unless a person asked.** No code path may push a branch, open a pull request, send a
  message or call a service on its own initiative. Publishing is per run and explicit.
- **Secrets never reach disk, logs or prompts.** Task text is redacted (`internal/sandbox`) before anything is
  stored. Do not weaken the redaction rules, the scrubbed environment, the loopback-only server, the key check or
  the "authors" requirement on GitHub watches. A change there needs a test that shows the old behaviour was
  unsafe or the new one is not weaker.
- **The cockpit builds the page with DOM calls, never from strings,** and has no inline script or style (its
  content policy forbids both; a test checks this). Agent output is untrusted text.
- **Works on Windows, macOS and Linux.** Use `filepath`, not string paths. Do not assume `sh`. The tests run on all
  three in CI.
- **Few dependencies.** The only one is `gopkg.in/yaml.v3`. Do not add another without a strong reason.
- **Messages are for people.** An error says what happened and what to do next, in plain sentences.

## Where things are

```text
cmd/legatus            the program          internal/engine      walks a run through its workflow
internal/cli           the commands         internal/pool        accounts, leases, limits
internal/server        API + cockpit (ui/)  internal/queue       workers, cancel, retry, resume
internal/agent/*       backends             internal/automation  schedules and the GitHub watcher
internal/store         runs as plain files  internal/github      gh: issues and pull requests
internal/worktree      git worktrees        internal/sandbox     redaction and the scrubbed environment
```

## What not to do

- Do not touch files outside this worktree. In particular not `~/.codex`, not the user's Legatus folder
  (`%APPDATA%\legatus` or `~/.config/legatus`), and not other repositories.
- Do not commit, push or change git configuration. Legatus commits your work when you finish.
- Do not put any "generated by", "co-authored by" or similar attribution in code, comments, commit text or
  documents. The work is the maintainer's.
- When you cannot do something, say so in your final message and say exactly why. A reply that claims success
  for work that was not done is the worst outcome.
